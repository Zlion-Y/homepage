# 复盘：交互 GPU 优化（毛玻璃快照）为何被整体回退

> 时间：2026-09-30 ~ 10-01 · 状态：**canvas 版已回退（edcdff3）；CSS 版 v1（5cad5e2）已于 2026-10-01 恢复** · 结论：视觉一致性优先于交互 GPU 占用

## 一、问题

用户设备 2560×1600@120Hz，页面 13 张 `.glass` 毛玻璃卡（`backdrop-filter: blur(14px) saturate(1.4)`）。

**已解决**（保留）：空闲 GPU 50%+ 的主因是常驻无限 CSS 动画（极光漂移、冒号呼吸、监控灯闪烁、
打字机光标）逼合成器每个 vsync 出帧 × 13 张毛玻璃卡每帧全屏重合成。修复：极光漂移与光标
闪烁改 JS 定步进驱动（轨迹与原动画逐点一致），其余删除。空闲 GPU 降到 ~4-5%。

**未解决**：交互时 GPU 飙升——鼠标划过卡片 47~78%，全屏播放+鼠标 68.7%。测量口径：
有头 Chrome + Windows「GPU Engine」性能计数器（任务管理器同源数据）；无头浏览器测不出
合成器差异（rAF 停摆、出帧行为不同），必须实测。

## 二、方案：毛玻璃快照（frost）

原理：桌面端页面不滚动，卡片背后的壁纸是静态的——`backdrop-filter` 的输出永远不变，
但任何脏区（光标/涟漪/倾斜）碰到卡片都会让 Chromium 逐帧重跑这份模糊。于是把「壁纸
cover + 36% 压暗 + 颗粒 + 6% 玻璃底色」按视口对齐一次性烘焙成静态纹理，撤掉实时
`backdrop-filter`。

效果（实测）：光标划卡片 47~78% → 22.6%；全屏播放中静止 63.1% → 8.8%；全屏播放+鼠标
68.7% → 27.9%。性能目标完全达成。

## 三、连环回归（为什么被回退）

快照把「实时取样」换成「预渲染纹理」，渲染路径变了，每一个细节差异都在真实壁纸上显形：

### 1. 卡片边框出现超细白边
- **现象**：所有卡片边框内侧一圈细白线。
- **根因**：`overflow: hidden` 把快照层裁在 **padding 盒**，而原版 `backdrop-filter`
  的取样延伸到**边框盒**——半透明边框圈后面失去了模糊取样，直接透出未模糊的原始壁纸。
- **修复尝试**：`clip-path: inset(0 round 18px)` 裁到边框盒 + `-1px` 内缩 outline
  在原位重画描边（负 z 子级按绘制顺序会盖住元素边框）。有效，但渲染路径又动了一次。

### 2. 抓取静止瞬间有一帧细微变化
- **根因**：倾斜动画结束后的合成层**降级重光栅化**，光栅分辨率切换产生单帧差异。
- **修复尝试**：frost 卡常驻 `will-change: transform` 保持图层提升。

### 3. 载入动画结束后仍能看到变化过程
- **根因**：快照挂载时机与入场 rise 动画竞态——动画中量取的 `getBoundingClientRect`
  带着 transform 位移（快照错位），且「实时取样 → 快照」的渲染路径切换落在动画收尾期
  被肉眼捕捉。
- **修复尝试**：轮询 `document.getAnimations()` 等入场动画真正播完再挂载。

### 4. 卡片光影变化（最严重）
- **现象**：载入几秒后所有卡片整体变暗、透出的内容结构改变。
- **根因**：随机壁纸 API（t.alcy.cc 等）**每次请求 302 到不同的随机图，且 302 本身
  不可缓存**（实测同 URL 三次请求三个 md5）。页面 `<img>` 拿到图 A，快照层的
  `background-image` 重新请求拿到图 B——卡片玻璃里是另一张图。
- **修复尝试 a**：同源服务端代理（`/api/wallpaper?u=`，Vercel 函数管道 + max-age 缓存）
  ——被否决：数据中心 IP 上游不稳、函数冷启动 + 中转 3.4s 撞探针超时，且多一跳依赖。
- **修复尝试 b**：canvas 绘制版——快照不再用 CSS 背景，改为每卡一个 `.frost-canvas`，
  用 `ctx.filter` 把「页面正在展示的那张壁纸 `<img>`（drawImage 只画不读，跨域源不受
  CORS 限制）+ 压暗 + 颗粒 + 底色」画进像素。技术上成立：高细节壁纸下快照与实时取样
  逐点采样 maxΔ≤3。

### 共同的验证盲区（为什么每轮都漏）
测试用的 fixture 壁纸是**平滑渐变**——对模糊而言线性渐变是恒等变换，**任何模糊半径、
甚至完全换一张图，在渐变上都测不出差异**。直到换用高频噪点图案壁纸才第一次真正测到
模糊保真度。此外本地 vite preview 会缓存启动时的文件清单，一度让回退验证跑了旧构建。

## 四、决策：整体回退

四个回归分属渲染管线不同环节，每个修复都动一次渲染路径、又暴露下一个差异，修不胜修。
项目最初的硬约束是「所有视觉感受和操作不能变化」——**视觉一致性优先于交互 GPU 占用**。
最终回退快照全部代码（CSS 版 / canvas 版 / 代理 / 时序补丁），卡片恢复原版实时
`backdrop-filter`。回退后 12 个界面状态与原版像素 diff 全部回到噪声级（面板
0.277%→0.007%）。

**回退时保留的成果**（与本问题无关或用户明确要求）：

| 保留项 | 说明 |
| --- | --- |
| 空闲 GPU 优化 | 常驻无限动画清零（极光 JS 步进、光标 JS 闪烁等），空闲 ~4-5% |
| 交互修复 | 倾角 5°、歌词加载可靠性（缓存自愈+重试+兜底源）、暂无歌词居中、全屏歌词高亮回归修复、歌单重开居中 |
| 全屏播放器 GPU | 移除反优化的 `will-change`、全屏打开时暂停被盖住两层内的动画（播放中静止 63.1%→8.8%） |
| 工程化 | lint / 单测 25 例 / 23 步全流程 E2E / 像素 diff 验证基建（vharness） |

## 五、代价与可选后续

- **代价**：交互时 GPU 回到高位（光标划过毛玻璃卡 ~50%，停手 1-2s 归零；全屏播放+鼠标
  ~28%）。这是「毛玻璃 + Chromium」的固有成本，静止时无影响。
- **可选后续**（均有可感知的视觉变化，需拍板）：模糊半径 14px→8px（玻璃更通透）；
  去掉自定义光标（消除光标脏区）；去 tilt 倾斜。三者任选都能进一步降交互 GPU。
- **技术备注**：「缓存第一次的背景」的正确客户端落地其实是 canvas `drawImage` 页面已
  展示的 `<img>`（只画不读，不受 CORS 限制），本方案已验证可行（maxΔ≤3）；若未来重启
  此方向，应从 canvas 版起步，并直接用真实照片壁纸做像素 diff。

## 六、经验教训

1. **对「像素级一致」硬约束的项目，替换渲染路径的优化必须用真实内容做像素 diff**——
   平滑渐变 fixture 对模糊是恒等变换，会让所有视觉差异测试全部失效（假绿）。
2. **出现第一个视觉回归就应放弃该路线**。渲染路径的替换（backdrop-filter → 快照）
   不是补丁能收敛的：每修一个差异就换一次渲染路径，再暴露下一个。
3. **性能测量必须在有头浏览器 + 系统 GPU 计数器下做**：无头环境测不出合成器差异，
   出过两轮假阴性/假阳性结论（「静态层代价在噪声内」「will-change 缓存纹理」均被推翻）。
4. **工程基建是有效的**：GPU 计数器按 PID 过滤定位真凶、12 状态像素 diff 守住回归、
   23 步 E2E 守住交互——回退后 diff 立刻归零，反向证明了方法可信。
5. 验证服务本身也要防陈旧：本地 preview 服务器缓存启动时的文件清单，曾让回退验证
   跑在旧构建上（数字完全不变暴露的）。

## 七、后续：v1 恢复（2026-10-01）

边框盒下（live 的 background-clip 默认 border-box，否则复发 1px 白边级回归）。
按教训 #2 放弃修补路线，整体恢复 CSS 版 v1 定稿（白边/闪帧/挂载时序修复齐全）。

**已知残留（2026-10-01 二次复核后改写）**：原文把残留写成「快照 CSS 背景重新请求随机
壁纸 API、302 换图」——**经线上站受控实验证伪**：同一次会话、同一张壁纸下把

## 八、载入时序整改：把所有渲染路径切换藏到遮罩后面（2026-10-01）

### 现象
首屏载入过程中，卡片边缘（内侧 1~6px 那一圈）会变一次——第七节里那句「残留在
载入数秒后出现」的真实内容。

### 根因
`.frost-ready` 挂载的那一帧，卡片同时换掉四样东西：撤实时 `backdrop-filter` 改吃烘焙
纹理（取样基准从「边框盒处截断」变成「60px 真实出血」）、`border` 改由 `outline` 原位
重画、`overflow` 放开、`::after` 出血层首次出现。边缘那一圈亮度必然变（实测 +18/255
上限，前两节量过），**这是渲染路径替换的固有代价，消不掉**。
而 v1 的挂载时机是「bg-ready + 1500ms → 等 `.page.ready` → 等字体 → 等入场动画播完」，
**整条链都落在揭幕之后**。实测基线（1256×565 headless，reduced-motion）：

| | 遮罩开始淡出 | 遮罩完全消失 | 快照挂载 |
| --- | --- | --- | --- |
| 基线轮次 1 | 1175ms | 1689ms | **2676ms** |
| 基线轮次 2 | 825ms | 1339ms | **1777ms** |
| 改后（壁纸快路径） | 1446ms | 1957ms | **1444ms** |

即基线把切换过程完整摆在观众面前（晚 0.44~1.0s），而带入场动画的真实浏览器只会
更晚（还要等 rise 播完，再加 ~1.35s）。

### 改法：把切换挪到遮罩还完全不透明的时候

链路从 `壁纸就绪 → 揭幕 → (+1500ms) 快照挂载` 改成
`壁纸就绪 → 等字体 → 量几何 → 烘焙 → 才允许揭幕`。五处改动：

1. **提前烘焙本来就可行**：`.page.ready .rise` 这个选择器意味着**揭幕前根本没有入
   场动画**，卡片静止在最终位置——几何本来就该在这时候量。v1 之所以要「等动画播完
   再挂」，只是因为它的挂载发生在动画之后（第三节第 3 项那条修复的由来）。
2. **揭幕门闩**（`App.vue`）：揭幕条件改为「落定时机到 → 最多再等 500ms 快照就绪」。
   ⚠️超时预算必须**从落定时刻起算**：写在 `Promise.race` 外层的话，壁纸慢于 800ms
   时它早就烧完了，等于没兜底。超时即揭幕，绝不让观感为它让路。
3. **背景也要在揭幕前落定**（`Background.vue` 的 `.snap`）：壁纸若在揭幕前到达，
   直接铺上不淡入——那段时间整屏被不透明遮罩盖着，淡入反正看不见；铺满之后揭幕那
   一刻背景已是最终状态，快照与实时 `backdrop-filter` 的基准才一致。否则会出现
   「卡片已按最终壁纸烘焙、背景还在从近黑淡入」的错配（比边缘差异更显眼）。
   晚于揭幕才到（极光兜底之后）保留淡入——那条路径本来就没有遮罩可用。
4. **壁纸尺寸走 wallpaperBus**：快照的 cover 尺寸原本靠 frost 自己 `new Image()` 再
   加载一次拿 `naturalWidth/Height`，而这一步正好卡在揭幕门闩的关键路径上（缓存不
   友好的源就是又一次网络往返）。Background 的探针加载时本就知道尺寸，直接传。
5. **布局监护**（新增，同时修掉 v1 的隐藏缺陷）：快照按挂载那一刻的几何烘焙，之后
   任何布局位移（天气卡要等接口到位才插入、RSS 列表从「正在获取…」变三条、字体
   回流）都会让整页推移，快照与壁纸整体错位。v1 完全没处理，只是恰好因为挂得足够晚
   而没暴露；提前到揭幕前烘焙就会撞上。`scan` 每秒比对几何指纹，变了就重烘焙。
   指纹必须是**视口里的绝对布局位置**，两个坑都实测踩到了：
   - 用 `getBoundingClientRect` → 含 tilt 的 3D 变换，鼠标划过卡片就变（误触发）；
   - 只用 `offset*` → 相对 `offsetParent`，而 `offsetParent` 在运行期会换（实测右列
     卡片的锚点从 `.page` 换到过另一个定位祖先，位置一动没动、指纹却整体换了坐标系），
     结果是反复重烘焙——**揭幕后重烘焙等于把切换又暴露一次**，第一版整改就栽在这里。
   - ⚠️**这两条在第九节被推翻**：第三版折中成「`offsetParent` 的 rect + `clientLeft/Top`
     + 自身 `offset*`」，仍然被祖先的 transform 污染（原因见第九节）。真正的解是
     「沿 `offsetParent` 链累加 `offsetLeft/offsetTop`」——不含任何 rect。

### 验证方法（可复用）
CDP 在**文档创建前**注入打点脚本（`Page.addScriptToEvaluateOnNewDocument`），用
MutationObserver 记录 `.page.ready` / `.glass.frost-ready` / 遮罩淡出起止的时间戳，
另每 50ms 采一次各卡的几何指纹。判据只有一条：
**最后一张卡的 `frost-ready` 必须早于 `mask:leave`**（遮罩此刻仍 opacity:1，其后的
0.5s 淡出则无所谓）。改后实测 1444ms 挂载 / 1446ms 起淡，两轮复现。

### 仍然存在的问题（知情接受）
- 极光兜底路径（壁纸晚于 2.8s 兜底揭幕才到）：没有遮罩可藏，快照挂载与壁纸淡入
  同时发生——但那时整屏背景本来就在换，边缘那点差异被淹没。实测该路径
  `mask:gone` 3345ms → `bg:img-fade` 4565ms → `frost` 4568ms。
- 二级面板卡片：面板 `display:none` 时量不到几何（rect 恒为 0），只能等可见后才
  烘焙，所以每次打开面板仍会走一次同样的切换（v1 行为，未改；要修得先让面板以
  `visibility:hidden` 常驻布局，属于另一笔交易）。

## 九、二轮整改：指纹被祖先 transform 污染 + 烘焙再推到门闩（2026-10-01）

### 现象（用户复述）
「模糊捕捉太快了，卡片还没到位就快照了模糊，导致卡片到位后又重新模糊快照了一次，
快照变化了一次能够观察到」——首屏已经可见之后，快照还会整体变一次。

### 根因：指纹取的是**被祖先 transform 污染的 rect**
第八节第 5 条把指纹写成「`offsetParent.getBoundingClientRect()` + `clientLeft/Top` +
自身 `offset*`」，注释里还特意声明是为了避开 `offsetParent` 换锚点。但这两件事互为因果：
**祖先一旦被 transform（`.rise` 入场动画），它自己就变成新的 `offsetParent`**，而它的
rect 带着动画位移、每帧都在变 → 监护在整段入场动画里反复判定"布局变了"→ 摘掉重烘焙。
入场动画恰好整段落在揭幕之后（rise 从 `.page.ready` 起播 0.8s + 错峰到 ~1.35s），
于是这次重烘焙必然被看见 —— 用户看到的就是「卡片到位后又重新模糊了一次」。

线上抓证据（给 `classList.add/remove` 打桩记录调用栈，栈全落在 frostCard / unfrostCard
这条监护路径上）：

| 时刻 | 动作 | 卡片 | 当时算出的指纹 | 静止时 |
| --- | --- | --- | --- | --- |
| 1103ms | unfrost | clock | `891,49,307,150` | `891,32,307,150` |
| 1103ms | unfrost | weather | `552,231,646,150` | `552,214,646,150` |

差的那 17px 就是 `.rise` 当时把卡片顶上来的位移。更漂亮的一条独立佐证是**中招集合**：
被反复摘除的只有 `hito / clock / weather / site-card×2`——**正好是 `.right-col` 的全部
卡片**；左列的 `greet / blog` 一次都没中。因为 `rise` 加在 `.right-col` 上（它是那 5 张的
`offsetParent`），而左列两张是各自带 `.rise`（transform 在自己身上，不影响自己的 offset）。

同时排除的另一条猜想——「接口数据晚到导致布局推移」：天气卡实测 292/161ms 就插进来了
（比烘焙早得多），右列推移 182px 全部发生在揭幕前；`.container` 的 `align-content:center`
也没有因它重居中（容器高不变）。数据晚到是**另一条真实但不同的**问题，见本节末。

### 改法（两处，互相独立）
1. **指纹改成沿 `offsetParent` 链累加 `offsetLeft/offsetTop`**：纯布局量，不含任何
   transform，也不依赖某一个锚点 —— 换锚点与 transform 两个误判源一起消掉。
2. **烘焙时机从"壁纸一就绪"再推迟到"揭幕门闩上"**，并在链里加一步**等布局落定**
   （连续两次采样指纹一致，上限 200ms）：`揭幕时机到 → 等字体 → 等布局落定 → 量几何
   → 烘焙 →（等一帧画出去）→ 才揭幕`。理由：天气卡、RSS 列表都是接口到位才插入的
   （`v-if`），快照必须在它们进来之后量；烘早了，监护就得在揭幕后重烘一次 —— 那又是
   一次可见变化。挪到门闩后，揭幕前所有布局变动都已经吃进几何里。

### 验证
⚠️**两次测量工具本身的坑，先修工具再下结论**：
- headless Chrome 默认 `prefers-reduced-motion: reduce`，**入场动画根本不跑** → 这条
  路径测不出来（第八节那次"两轮都没重烘焙"的假阳性就是这么来的）。必须
  `Emulation.setEmulatedMedia` 打开动画，并回读 `matchMedia(...).matches` 确认。
- 用 MutationObserver 看 `frost-ready` 的增删**会系统性漏掉重烘焙**：`scan()` 一次迭代
  里先 `unfrostCard` 后 `frostCard`，两次类名改动在同一个同步任务内，回调跑的时候类名
  已经加回去了。必须直接给 `classList.add/remove` 打桩。两种量具的结论**完全相反**
  （observer 版："偶发，5 轮 1 次"；打桩版："3/4 轮命中，每轮 9~10 张"）。

| 版本 | 每轮重烘焙/摘除 | 4 轮结果 | 旧指纹揭幕后变化 | 新指纹揭幕后变化 |
| --- | --- | --- | --- | --- |
| 线上（改前，= `12708b8`） | **9~10 次** | FAIL 3/4 | 30~35 次 | — |
| 本地（改后） | **0 次** | **PASS 4/4** | 30~35 次 | **0 次** |

改后每一轮里旧指纹仍然变了 30~35 次（说明触发条件一直存在，不是"没触发所以没重烘焙"），
新指纹 0 次。留这组交叉数据是为了让"修好了"可证伪。

### 残留：数据比烘焙还晚到（真实布局推移，监护会修正但修正本身可见）
把天气接口人为延迟 1.8s 复现：烘焙 1249ms（6 张卡，天气不在 DOM）→ 揭幕 1268ms →
天气 1885ms 进 DOM → 2032ms 补烘天气卡 → **2034/2035ms 两张 site-card 被摘除重烘**
（它们被推移了 182px）。即：监护确实把快照修正了（不会永久错位），但那次修正发生在
可见时段。要在"接口慢"的情况下也不出现，只有两条路：
- **让揭幕等首屏数据**（天气/列表到位或判定失败，有界兜底）——正常网络下数据在
  75~330ms 就到，几乎不增加等待；接口慢时最多多等这个上限。
- **给天气卡预留占位**（`v-if` 换成等尺寸占位）——零延迟、零推移，代价是接口慢/失败时
  卡片位置留一个 150px 空洞。
两条都不是"改错"，是产品取舍，未擅自实施。
